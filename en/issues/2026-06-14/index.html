When execution gets cheap, verification and work design become the product

Stronger agents finish more often, but the new dominant failure is a plausible wrong result. The winner is not the company with the most AI tools, but the one that standardized context, access, verification, release, and accountability.

Published · 15–18 min read

Chapter 01

A new production system

Story 01

Stronger agents finish more work—and can finish it incorrectly

As capability rises, the problem shifts from 'the agent stopped' to 'the agent confidently delivered the wrong result.' Verification becomes a separate production loop.

In Workflow-GYM, the best models completed only a little more than 30% of long tasks: Gemini 3.1 Pro reached 30.67% pass@1 and Kimi-k2.6 reached 41.42% pass@3. Tasks required 30–110 atomic actions. An early error changed the state, after which locally reasonable actions relied on false premises. As models grew stronger, the dominant failure shifted from non-completion to incorrect completion.

CoDA-Bench adds a second cause. Even the best agents failed to find the correct data in almost 20% of tasks, and accuracy in some environments above 8 GB approached zero. Oracle context raised Claude from 45.4% to 73.1%, yet average accuracy with correct data was still about 71%. Context discovery and correct execution are independent failure sources; more interaction rounds do not remove them.

A production harness is layered. Cheap deterministic checks—types, schemas, checksums, and business rules—run every time. A separate skeptical agent checks meaning and missing requirements. For high-stakes work, a person accepts the final result against a predefined protocol. In one reported project this raised success from 20% to almost 100% without changing the model, yet AI-generated functional tests still do not justify removing human review.

This changes product economics. The unit of value is not a token or agent run but a proven correct completion. Measure false completion, recovery rate, bad-context detection, and verification cost per accepted result. Those metrics reveal where an expensive model, second agent, and human reviewer pay for themselves.

Story 02

Shopify standardized the shared layer beneath AI tools, not one tool

Choosing one permanent AI vendor is premature. A more durable choice is a common access, context, and control layer above which teams can switch tools.

Shopify routes requests from different AI tools through an internal LLM proxy. It centralizes cost control, usage analytics, and model substitution without forcing one interface on engineers. MCP servers let assistants reach Salesforce, Slack, GitHub, and internal wikis under the same access controls as normal employee authentication. The gateway, identity, and observability are standardized—not the copilot.

The second layer is release management. Ramp separates early access from general availability: about 10% of customers, more than 5,000 companies, form an embedded test group. A team can move quickly inside early access, while general release opens after evidence. Speed remains local while risk is limited by cohort and a formal stage gate.

The third layer protects against comprehension debt. Rollback rates do not show whether a team understands the system it created. Demos, architecture reviews, and the ability to diagnose failures several layers down are still required. With multiple parallel agents, the senior engineer's job becomes rejecting bad branches, merging good ones, and preserving the team's system model.

The enterprise pattern is concrete: model gateway, unified identity and permissions, connectors to systems of record, cost and quality logs, evals, release tiers, and an accountable owner. That layer allows tool experimentation without uncontrolled data, spend, and unsupported workflows.

Story 03

AI compressed coding while raising the value of specification, verification, and ownership

The bottleneck did not merely move to code review. It spread across deciding what to build, proving it works, and preserving system understanding among the people accountable for production.

In SWE-chat, only 44% of agent-generated code survived into user commits. Another study found an eightfold increase in lines written by AI agents but only a 30% increase in releases. Artifact volume grows much faster than the capacity to decide, verify, and ship value.

AI as Normal Technology identifies three persistent constraints: product specification; verification and responsibility; and deep knowledge of the codebase and business. Developers in SWE-chat used agents more often to understand existing code than to create new code—19% versus 13%. The more changes are generated, the more valuable it becomes to distinguish a locally working patch from a system-safe answer to the actual business problem.

The junior-market story therefore cannot rest on the floating claim that demand is 'collapsing'; this issue does not contain evidence for it. A better-supported signal is that some execution work used for apprenticeship is disappearing. Companies need a new ladder: reviewing generated changes, reproducing incidents, building evals, shadow ownership, and explaining architecture decisions.

For founders, this changes hiring and measurement. Engineer value shifts away from typing speed toward problem quality, verifiable system design, domain knowledge, and ownership. Measure releases, defects, cycle time, and system comprehension—not lines of code or accepted suggestions.

Chapter 02

New systems of record and markets

Story 04

The next system of record will store decision context, not only transactions

A 'live company context' is a continuously updated event layer that can reconstruct who made a decision, from what evidence, and in which state—before a transaction or document appeared.

a16z predicts a new class of enterprise software around recorded voice and work interactions. The point is not an archive of every meeting. Conversations, messages, and actions are resolved into entities, commitments, reasons, and links to CRM, ERP, or accounting objects. The record can then answer not only what changed, but which agreement, data version, and person produced the change.

This matters most in financial exceptions. A payment classification, revenue decision, accepted source document, or reserve adjustment should link to the originating file, discussion, rule, model version, and responsible approval. Such an event log both teaches the agent the company's real context and makes its actions auditable later.

Recording everything also creates risk. Identity, timestamp, immutable event versions, read permissions, retention policy, correction history, and a distinction between raw record, extracted fact, and approved decision are mandatory. Without them, live context becomes a confident reconstruction that is neither accounting evidence nor a safe basis for action.

The entrepreneurial opportunity is a contextual ledger between systems of record rather than one LLM replacing them. It can become an enterprise control plane: collect reasons, route exceptions, provide minimal context, and write verified outcomes back into ERP.

Story 05

In agentic commerce, a product can be removed from consideration before the interface

When a buyer delegates discovery and comparison to an agent, the primary shelf becomes a set of machine-readable facts the model can trust.

Deloitte reports that 55% of consumers now begin shopping through LLMs. An agent need not expose the whole assortment: it interprets intent, narrows options, compares constraints, and may place the order. Incomplete, contradictory, or stale SKU data can remove a product from the consideration set without an explicit human rejection or a signal in traffic metrics.

The new optimization stack has five layers: structured SKU data; authoritative real-time price, inventory, and policy APIs; verifiable claims; trust infrastructure for seller identity, review integrity, fraud, and post-purchase resolution; and observation of why agents recommend, substitute, or exclude products. Replenishment, subscriptions, and B2B ordering are natural pilots because intent repeats.

Platforms face a deeper risk. An agent may form the choice before search, marketplace, or app, reducing the platform to an interchangeable execution layer. Impressions and clicks no longer prove influence, attribution weakens, and monetization moves toward measurable decision influence and transaction outcomes.

This creates a B2B market for agent-ready catalogs, trust APIs, algorithmic-shelf monitoring, and optimization for machine selection. The early winner may not be the loudest brand, but the supplier whose data is easiest to verify, compare, and safely act upon.

Story 06

LLMs show no clear network effect, so the moat must sit above the model

A model can be huge and expensive without becoming a platform with a self-reinforcing network effect.

Benedict Evans notes that LLMs have not shown an Instagram-, YouTube-, or Google Search-like loop in which every user improves the product and attracts the next. He estimates the relevance of a particular model in months—roughly three to six or six to nine. Meanwhile cheaper software development should increase competition by making formerly uneconomic vertical applications viable.

Model commoditization does not mean product commoditization. Much enterprise work is undocumented, absent from training data, and impossible for employees to fully express as a process map. Advantage comes from turning that tacit context into permissions, tools, feedback data, evals, and an embedded route to the result.

Practitioners already treat frontier APIs as unstable dependencies: they preserve model portability and continuously validate outputs through evals and harnesses. This confirms the first issue's electricity thesis: the model supplies a resource while value accumulates in the applied system.

A defensibility review should ask five questions: do you own a usage-data loop; does the workflow improve with every case; is the product hard to remove from the system of record; do you own trust and distribution; can the base model be replaced without losing customer value? If not, vendor model progress is more likely to erode the product's advantage than strengthen it.
